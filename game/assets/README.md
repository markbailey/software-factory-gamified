# Software Factory sprites

Original hand-authored SVG artwork (generated by `../tools/gen_sprites.py`, so the set stays consistent; edit the script and re-run rather than editing files by hand). 101 static sprites, 20 GUI theme icons (see [GUI theme](#gui-theme)), plus 498 animation frames and 58 Godot `SpriteFrames` resources in `belts/anim/` and `machines/anim/` (see [Animation](#animation)). Belt merges, splits and crossover bridges are described in [Junctions](#junctions).

## Grid and conventions

- Square grid, `CELL = 64` px, top-down view, light from the top left.
- Outline `#16181C`, about 2 px. Floor base colour `#292B30`.
- Every file has explicit `width`/`height`/`viewBox`, no text, fonts, filters, masks, clip paths, `<style>` or external references. Only shapes, paths, group transforms, and linear/radial gradients (plus `stroke-dasharray` in `overlay_failed.svg`, `splitter.svg`, `merger.svg` and `fill-rule="evenodd"` in `icon_settings.svg`). The junction belts also use `scale(1 -1)` in a group transform (mirrored variants) and plain `opacity` on black rectangles for the bridge shadow; they contain no gradients.
- Anchor: top-left of the image = top-left of the footprint. No padding to compensate for (machine bodies start 4 px in; scrap bin lugs reach 1 px from the edge).

## belts/ (64x64)

Band is 36 px wide and centred (14..50), rails 5 px on both sides (9..14, 50..55), chevrons point in the direction of travel.

- `belt_straight_<dir>.svg`: travel direction `e`, `w`, `n`, `s`.
- `belt_corner_<from>_<to>.svg`: items **enter through the `<from>` edge** of the tile and **leave through the `<to>` edge**. Example: `belt_corner_w_n` connects the west and north edges, moving toward north. All 8: `w_n w_s e_n e_s n_e n_w s_e s_w`.
- `belt_end_<dir>.svg`: end cap (roller and yellow stop) on the `<dir>` side; travel toward `<dir>`.

Picking a tile from the previous and next cell: `from` = side the previous cell is on, `to` = side the next cell is on. If they are opposite, use `belt_straight_<to>`.

Clockwise loop: `s_e` (top-left), `w_s` (top-right), `n_w` (bottom-right), `e_n` (bottom-left). Counter-clockwise: `e_s`, `s_w`, `w_n`, `n_e`.

A closed loop or a U-turn needs no special piece: it is built from these corners (two corners back to back make a U-turn, e.g. `corner_w_s` above `corner_n_w` turns an eastbound belt back west one row down). A line that rejoins **itself** needs the junction pieces below.

## Junctions

24 more belt tiles in `belts/` (64x64, same band, rails and palette), each with an 8-frame animation in `belts/anim/`.

### Side-feed merge T: `belt_merge_<through>_from_<side>.svg`

A straight through-belt travelling toward `<through>`, plus a feeder that **enters through the `<side>` edge** and joins it.

- In: the edge opposite `<through>` (through belt) and the `<side>` edge (feeder). Out: the `<through>` edge.
- Example `belt_merge_e_from_n`: through belt west -> east, feeder comes in through the north edge moving south.
- All 8: `e_from_n e_from_s w_from_n w_from_s n_from_e n_from_w s_from_e s_from_w`.
- The feeder curves toward the direction of travel (same arc as a corner piece) and ends at a steel transfer lip on the through band. The rail on the feeder side is open; the opposite rail is unbroken.

### Side-output split T: `belt_split_<through>_to_<side>.svg`

A straight through-belt travelling toward `<through>`, plus a branch that **leaves through the `<side>` edge**.

- In: the edge opposite `<through>`. Out: the `<through>` edge (straight on) and the `<side>` edge (branch).
- Example `belt_split_e_to_s`: through belt west -> east, branch leaves through the south edge moving south.
- All 8: `e_to_n e_to_s w_to_n w_to_s n_to_e n_to_w s_to_e s_to_w`.
- Marked by a yellow diverter flap hinged on the downstream corner of the branch opening. That flap (and the branch chevrons running away from the band) is what tells a split from a merge. The flap does not move in the animation.

### Crossover bridge: `belt_cross_<lower>_<upper>.svg`

Two belts crossing at 90 degrees without joining. The belt travelling toward `<lower>` stays on the floor; the belt travelling toward `<upper>` crosses on a raised deck (lighter side girders, drop shadow on the lower belt toward the bottom/right).

- Lower belt: in through the edge opposite `<lower>`, out through `<lower>`. Upper belt: in through the edge opposite `<upper>`, out through `<upper>`.
- All 8: `e_n e_s w_n w_s n_e n_w s_e s_w`.
- About 7 px of the lower belt shows on each side of the deck. With the usual draw order (belts, then crates) a crate on the lower belt would be drawn on top of the deck, so the game should hide a lower-belt crate while it is under the deck (centre within about 23 px of the tile centre along the lower belt's axis). Crates on the upper belt need nothing special.

### Composing a self-joining loop

A rework loop that leaves the main line and feeds back into it earlier (main line west -> east on row 1, loop below it):

```
row 1:  straight_e  merge_e_from_s  straight_e  straight_e  straight_e  split_e_to_s  straight_e
row 2:              straight_n                                           straight_s
row 3:              corner_e_n      straight_w  straight_w  straight_w  corner_n_w
```

1. Put `belt_split_<through>_to_<side>` where the loop leaves the line.
2. Run the return path with ordinary straights and corners. The first tile after the split is entered from the split's `<side>` edge, so pick it with the usual from/to rule.
3. Put `belt_merge_<through>_from_<side>` where the loop comes back, upstream of the split. The last return tile must exit toward the merge.
4. If the return path has to get to the other side of the line (or cross any other belt), use `belt_cross_<lower>_<upper>` at the crossing, e.g. `belt_cross_e_n` lets a northbound return path bridge over an eastbound main line.

A loop can also rejoin downstream of where it left (a bypass): same pieces, split first, merge later.

Picking a junction tile in code: a belt cell with two inputs and one output is a merge, one input and two outputs is a split, and two independent straight belts in one cell is a cross.

```gdscript
# out_dir: direction of the through belt; side: the extra edge ("n", "e", "s", "w")
func junction_piece(kind: String, out_dir: String, side: String) -> String:
    match kind:
        "merge": return "belt_merge_%s_from_%s" % [out_dir, side]
        "split": return "belt_split_%s_to_%s" % [out_dir, side]
        _:       return "belt_cross_%s_%s" % [out_dir, side]   # lower dir, upper dir
```

**Routing is game logic, not art.** The sprites only show that a junction exists. Which crate takes the branch at a split (alternate, filter by state, send failures back for rework), who has priority at a merge, and how to stop a full loop from blocking the line are all decided by the simulation. Crate motion through a merge or split can follow the through belt's straight line, or for the side path the same quarter arc as a corner piece (radius 32 px about the tile corner between the `<side>` edge and the downstream end for a merge, the upstream end for a split).

### Risk stamps

`risk_low.svg`, `risk_medium.svg`, `risk_high.svg`: the result the risk analyser stamps on a crate, read later by the reviewer (auto-approve or ask a human). Each is a **standalone 32x32 badge that fills the canvas**, not a crate variant and not a pre-positioned overlay; the game scales it down and places it on the crate.

| File | Shape | Bars | Colour |
|---|---|---|---|
| `risk_low.svg` | circle | 1 (white) | green `#5ABF66` |
| `risk_medium.svg` | triangle | 2 (dark) | amber `#F2B84C` |
| `risk_high.svg` | chamfered square | 3 (white) | red `#E5484D` |

- The levels differ by shape and bar count as well as colour. Outline is 3.5 px at 32 px so it survives the downscale.
- Draw it at about **14x14 px in the crate's bottom-left corner**: top-left of the badge at crate top-left + (2, 16), i.e. belt-cell centre + (-14, 0). The previews use exactly this.
- Draw order per crate: crate sprite (`crate`, `crate_issue`, `crate_pass`, `crate_fail`, which already contain the pass/fail stamp in the centre and the issue tag), then the risk badge on top. If the game ever draws those parts separately, the order is crate, pass/fail stamp, risk badge, issue tag.
- Where things sit on the 32 px crate: pass/fail stamp is a circle of radius 9 in the centre; the issue tag in `crate_issue.svg` is the triangle in the **top-left** corner (4,4)-(19,4)-(4,19) (if the game moves or draws its own issue tag in the top-right corner, that corner is free as well). The bottom-left badge covers the lower-left rim of the pass/fail circle by a few pixels; the check and the X stay readable. The bottom-right corner is the only one that touches neither.

const RISK_TEX := {

## Using them in Godot 4

Copy this folder to `res://assets/`. Godot imports each SVG as a `Texture2D` (rasterised at import; raise "SVG > Scale" in the Import dock for HiDPI).

```gdscript
const CELL := 64
const TEX_CODER: Texture2D = preload("res://assets/machines/coder.svg")
const TEX_RUNNING: Texture2D = preload("res://assets/machines/overlay_running.svg")
const TEX_CRATE: Texture2D = preload("res://assets/crates/crate.svg")
const LAMP := Vector2(110, 14)

func _draw() -> void:
    # machine: top-left cell (cx, cy), 2x2 footprint
    var origin := Vector2(cx, cy) * CELL
    draw_texture_rect(TEX_CODER, Rect2(origin, Vector2(128, 128)), false)
    # state: lamp dot and frame overlay
    draw_circle(origin + LAMP, 4.5, Color("4C8DF2"))
    draw_texture_rect(TEX_RUNNING, Rect2(origin, Vector2(128, 128)), false)
    # crate centred on a belt cell (bx, by), plus travel offset along the belt
    var centre := (Vector2(bx, by) + Vector2(0.5, 0.5)) * CELL
    draw_texture_rect(TEX_CRATE, Rect2(centre - Vector2(16, 16), Vector2(32, 32)), false)
```

- Overlays already carry their state colour; pass a `modulate` colour with lower alpha as the last argument of `draw_texture_rect` to pulse them.
- Belts need no rotation: pick the file by name, e.g. `load("res://assets/belts/belt_corner_%s_%s.svg" % [from, to])`.
- Draw order: floor, belts, crates, machines, overlays.

| `machines/anim/` | `<machine>_run_f0..f7.svg` (all 13) | 8 | 8 (1 s) | 104 SVG |
| `machines/anim/` | `<machine>_idle_f0..f1.svg` (all 13) | 2 | 2 (1 s) | 26 SVG + 13 `.tres` |

`<piece>.tres` / `<machine>.tres` are Godot 4 `SpriteFrames` text resources (format 3, `ext_resource` by `res://assets/...` path, no uids; Godot adds uids when it re-saves them). Belts have one animation `default` (12 fps, loop). Machines have `idle` (2 fps, loop) and `running` (8 fps, loop).

### Belts

- The surface (chevrons every 16 px, slats every 8 px) advances 2 px per frame, so 8 frames = one 16 px period and `f7 -> f0` is seamless. Rails, rivets and the end-cap stop are static. At 12 fps the surface moves 24 px/s; if crates move at a different speed, set fps = crate speed in px/s divided by 2.
- Tiling: the pattern is defined by distance from the tile's **entry edge**. A straight tile is 4 periods long. A corner is 3 periods long, stretched 4.7% along the centreline arc (50.27 px) and bent with it, so the phase at every entry and exit edge is the same on every tile and every frame. A chevron crossing a tile edge is drawn half by each tile and the halves meet exactly.
- **Every belt tile must show the same frame index at the same time.** Drive them all from one global clock, not per-tile timers. Tiles that start their animation at different times will show a jump at the shared edge.
- The animated belts carry 4 chevrons per tile (the static ones carry 3), so do not mix static and animated belt tiles in one line. For a stopped belt, hold all tiles on the same frame.
- End caps: the surface runs under the roller (clipped by geometry); the roller highlight alternates between two positions.
- Junctions follow the same phase rule, so they line up with straights and corners on every frame. Merge and split: the through belt is an ordinary straight surface; the feeder or branch uses the corner pattern (3 periods over the arc, measured from the feeder's entry edge, or ending on a whole period at the branch's exit edge) and is cut off by geometry at the transfer lip. Cross: both belts are ordinary straight surfaces; the lower one runs under the deck. The animated junctions carry the animated chevron spacing (4 per tile), the static ones the static spacing, same as the other belts.

### Scrap bin drop (one-shot)

`machines/anim/scrap_bin_drop.tres` has one animation, `drop` (6 frames, 12 fps, `loop` false): a scrapped crate with the red X stamp falls onto the heap from above (drawn large, shrinking), lands on frame 3, squashes while the crates under it jump on frame 4, and settles. The frames are full 128x128 bin sprites drawn over the `full` load, and **`scrap_bin_drop_f5.svg` is identical to `scrap_bin_full.svg`**, so the hand-over to the static `full` sprite is invisible. When a crate arrives: update the count, play `drop`, and on `animation_finished` show `scrap_bin_full.svg`. On the first crate (bin was empty) the heap appears on frame 0 under the falling crate. The count badge region stays clear on every frame. The existing `scrap_bin.tres` (`idle`, `running`) is unchanged and belongs to the original `scrap_bin.svg` load.

```gdscript
const BIN_STATE := {
    "empty": preload("res://assets/machines/scrap_bin_empty.svg"),
    "full": preload("res://assets/machines/scrap_bin_full.svg"),
}

func on_crate_scrapped() -> void:
    count += 1
    drop_sprite.visible = true            # AnimatedSprite2D with scrap_bin_drop.tres, centered = false
    drop_sprite.play("drop")
    await drop_sprite.animation_finished
    drop_sprite.visible = false
    bin_sprite.texture = BIN_STATE["full" if count > 0 else "empty"]
    # then draw the count badge in code inside x 96..124, y 4..24
```

### Using the animations in Godot 4

With nodes:

```gdscript
var spr := AnimatedSprite2D.new()
spr.sprite_frames = preload("res://assets/machines/anim/coder.tres")
spr.centered = false                 # anchor = top-left of the footprint
spr.play("running")                  # or "idle"
```

For belts made of `AnimatedSprite2D` nodes, do not call `play()` on each tile. Set the frame of all of them from one clock so they stay in phase:

```gdscript
var belt_frame := int(Time.get_ticks_msec() / 1000.0 * 12.0) % 8
for b in belt_sprites:
    b.frame = belt_frame
```

With a single `Node2D` and `_draw()` (call `queue_redraw()` from `_process` when the frame index changes):

```gdscript
const BELT_FPS := 12.0
const BELT_N := 8
const RUN_FPS := 8.0
const RUN_N := 8
var belt_tex := {}     # "straight_e" -> Array[Texture2D] of 8 frames
var coder_run: Array[Texture2D] = []

func _ready() -> void:
    for piece in ["straight_e", "corner_w_s"]:   # every piece in use
        belt_tex[piece] = []
        for i in BELT_N:
            belt_tex[piece].append(load("res://assets/belts/anim/belt_%s_f%d.svg" % [piece, i]))
    for i in RUN_N:
        coder_run.append(load("res://assets/machines/anim/coder_run_f%d.svg" % i))

func _draw() -> void:
    var t := Time.get_ticks_msec() / 1000.0
    var bf := int(t * BELT_FPS) % BELT_N          # one index for ALL belt tiles
    for cell in belt_cells:                        # cell.piece e.g. "corner_w_s"
        draw_texture(belt_tex[cell.piece][bf], Vector2(cell.x, cell.y) * 64)
    var mf := int(t * RUN_FPS) % RUN_N             # machines may each use their own offset
    draw_texture(coder_run[mf], Vector2(cx, cy) * 64)
```

The frame textures can also be read out of the `.tres`: `sprite_frames.get_frame_texture("default", bf)`.
